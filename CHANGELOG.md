[1.2.1] 2026-07-08 — Recurrence of the 1.0.4 dialog crash: today's 12pm run's Indeed browser died within seconds (`ProtocolError (Page.handleJavaScriptDialog): Not attached to an active page`) and Indeed produced 0 applications, then a subsequent relaunch attempt hit `Timeout 180000ms exceeded`. Root cause is deeper than 1.0.4 addressed: the Node.js err.log shows the crash comes from Playwright's own internal `DialogManager.dialogDidOpen → Dialog.close → Dialog.accept` auto-close path racing against page teardown — not from our `_safe_dismiss()` handler, so wrapping that handler in try/except (the 1.0.4 fix) can't catch it; it's an uncaught exception inside the Node driver itself. Two changes in `indeed_apply_now.py`: (1) `_safe_dismiss()` now also checks `d.page.is_closed()` before calling `dismiss()` — narrows one race window, though not the one that crashed today. (2) The real fix: `main()` had no cleanup path if the browser session died before reaching `browser.close()`, so the Chromium profile's SingletonLock/Cookie/Socket files were left behind, and the next launch attempt (same run or next scheduled run) hung on the stale lock until Playwright's own timeout — this is what produced the follow-on `Timeout 180000ms exceeded`. Registered an `atexit` handler right after `launch_persistent_context()` that unconditionally removes those three lock files on process exit, clean or crashed. Also added `INDEED_BROWSER_LAUNCH_TIMEOUT_MS` (config.py, default 60000) and passed it as `timeout=` to `launch_persistent_context()` so a genuinely stuck launch fails in ~1 minute instead of 3, if this ever recurs. Syntax-checked (`py_compile`); Playwright wasn't available to live-test in this session (no browser/login session outside Raghav's Mac) — run `python3 indeed_apply_now.py --dry-run` before the next live run to confirm the lock-release and faster-fail behavior. Also reviewed and confirmed 1.2.0's scoring toggle is working as intended: `USE_CLAUDE_SCORING = False` in config.py, both `indeed_apply_now.py` (line 3408) and `linkedin_apply_now.py` (line 1917) correctly branch to the free `jd_parser.ats_fit_score()` for fit-scoring — no Claude/Anthropic API call for the apply/skip decision. The small haiku API costs still showing in run summaries (e.g. today's LinkedIn run: 10 haiku calls, $0.0125) are from unrelated, cheaper Claude calls — LinkedIn's grey-zone legitimacy/trust check and vision-based form-field validation — not fit scoring, exactly as noted in 1.2.0.

In the live pipeline this specific case is still caught by the earlier off-domain-title filter (nurse jobs are blocked there already), but anything that passes the loose title-keyword filter and still has domain/seniority mismatches Claude would normally catch may now get approved. Not fixed here — flagging for Raghav to watch over the next few runs. Note: this only changes the fit-scoring gate — LinkedIn's grey-zone legitimacy check and Indeed's batched snippet pre-filter still make their own (smaller, cheaper) Claude calls independent of this toggle, so cost drops significantly but isn't fully zero; not touched in this change since it wasn't part of what was asked.

[1.0.7] 2026-07-02 — Indeed no longer grinds for hours when the session is blocked. [1.0.8] 2026-07-02 — Fixed a real cause of stuck/failed applications: numeric fields ("How many years of X experience?") rejected by the site's own validation with "Answer must be a valid number (no decimals)" whenever Claude answered with a fraction (e.g. "2.5"). Also fixed data/stuck_questions.json always logging `"fields": []` for every stuck application (182/182 entries checked had this) — the field it read, `form_fields_last_seen`, was either never assigned (Indeed's fallback check `'form_fields_last_seen' in dir()`) or assigned via a broken `isinstance(form_ctx, dict)` check that's always False since form_ctx is a Playwright Frame, not a dict. [1.0.10] 2026-07-02 — Fixed the log-schema bug found during pro-level analysis: Indeed's cross-platform dedup (from 1.0.3) merged LinkedIn's entire apply_log.json directly into the in-memory `log` list that ALSO gets saved back to indeed_applied_log.json after every job. Two problems: (1) LinkedIn's log schema uses a "note" field for the skip/fail reason, Indeed uses "reason" — so every LinkedIn entry that leaked into Indeed's log looked reason-less. (2) Every Indeed run re-saved LinkedIn's entire history back into indeed_applied_log.json, which had ballooned to 119,126 records (49MB) — only 3,438 (2.9%) were actually Indeed's own. Fixed by keeping the merged LinkedIn data in a separate `dedup_log` used only for the already_applied() lookup; `log` (what gets appended-to and saved) now only ever contains Indeed's own entries. Also did a one-time cleanup of the existing indeed_applied_log.json: backed up to indeed_applied_log.json.bak_pre_cleanup_20260702_181631, then filtered out all linkedin.com-URL entries — file dropped from 119,126 records / 49MB to 4,953 records / 3.7MB. Failed-entries-with-empty-reason dropped from 97% to 12.1% (the residual 12% are genuine edge cases like bare exceptions with no message, not a schema issue).

[1.0.11] 2026-07-03 — Fixed three related "pipeline goes silent" bugs reported live during a CAPTCHA (Raghav solved it and submitted, pipeline kept waiting the full 10 minutes anyway):
(1) `_check_and_handle_captcha()`'s `still_captcha` check only tested whether the reCAPTCHA `bframe` iframe was still *attached* to the page (`"bframe" in f.url`). Google's reCAPTCHA never removes that iframe after a solve — it just hides it — so the check could never go False unless the whole page happened to hard-navigate. Replaced with a visibility check (computed `display`/`visibility`/bounding-rect) inside `page.evaluate`, with the old presence check kept as a fallback if evaluate throws.
(2) The `already_confirmed` fallback (looks for "application submitted" etc.) only read `page.body.innerText` on the top-level document, but Indeed's apply UI — including the post-submit confirmation — renders inside a nested iframe (the auto-click-Submit code a few lines down already knew this and loops `page.frames()`; the text check didn't). Now scans every frame's `document.body.innerText`, not just the top-level page.
(3) Separately: Indeed's "stop early after N consecutive 0-card searches" bail (added in 1.0.7 for the Cloudflare-block case, `INDEED_EMPTY_QUERY_BAIL_THRESHOLD`) never sent an email, unlike its sibling CAPTCHA-cooldown-exceeded stop which does. So a Cloudflare-blocked run went completely silent — no real-time alert, and since it also applied 0 jobs, `notify_session_done()`'s `if applied == 0: return False` guard suppressed the end-of-run summary too. Added a `notifier.send_alert()` call at the bail point so a blocked/Cloudflare-stopped run now emails immediately, matching the CAPTCHA-cooldown behavior. (Note: `notify_session_done`'s 0-applied suppression itself was left as-is — not touched in this change.)

[1.0.12] 2026-07-03 — Fixed the back-to-back CAPTCHA email spam reported right after 1.0.11 shipped. 1.0.11 made the wait-loop's "is it still showing" check visibility-aware, but missed that `_check_and_handle_captcha()`'s entry gate (`captcha_visible`, checked at the very top of the function, and called again after every Submit-retry attempt) still used the old presence-only check. Since reCAPTCHA never removes the bframe iframe from the DOM — only hides it — that gate stayed True for the rest of the job's session once a CAPTCHA had appeared even once. Result: every one of the up-to-8 Submit-retry attempts in the same job re-triggered the full "CAPTCHA DETECTED" alert + email + Mac notification, then immediately self-resolved via the (correctly fixed) wait loop — looking like a solved CAPTCHA kept reappearing every ~8 seconds. Fixed by extracting one shared `_captcha_actually_visible()` helper (the visibility check from 1.0.11) and using it at both the entry gate and inside the wait loop, so there's only one place this logic lives and it can't drift out of sync again.

[1.1.0] 2026-07-03 — New feature per Raghav's request: batched snippet pre-filter for Indeed search-result pages, instead of opening every surviving card's job page one at a time to find out if it's worth applying to. Indeed's card scrape (`_page_cards` in indeed_apply_now.py) now also captures each card's short on-page snippet (with an innerText fallback if Indeed's snippet class names change). New `claude_engine.prefilter_cards_batch()`: takes every card that already passed the existing free filters (title level, domain, staffing/consultancy, already-applied dedup) for one query, and makes a SINGLE haiku call covering the whole batch (up to ~45 cards) asking only "obviously wrong or worth a closer look?" using just title+company+snippet. Cards it flags obviously-wrong (senior/lead titles, unrelated domain, staffing agency) are skipped with zero page loads; everything else still goes through the existing full-JD score_fit() check exactly as before — this only adds a coarse gate in front of it, it doesn't replace the real scoring. Deliberately fails open (treats every card as "worth opening") if Claude is unavailable or the response can't be parsed, verified with unit tests simulating both a normal batched response and a garbage/unparseable one — a bad API response can never silently drop a job that would've been a real fit. Side benefit: fewer job-page navigations per query means fewer chances to trip Indeed's Cloudflare check, which has been the main cause of blocked sessions this week.

## How to log a change

Before making any edit:
```bash
bash safe_update.sh start "describe what you're trying"
```

After the change works:
1. Bump `PIPELINE_VERSION` in `config.py` (e.g. 1.0.0 → 1.0.1 for a fix, → 1.1.0 for a new feature)
2. Add a line here: `## [1.0.1] YYYY-MM-DD — what changed`
3. Run `bash safe_update.sh keep` to merge and save to GitHub

If the change breaks something:
```bash
bash safe_update.sh discard   # back to last working version instantly
```
